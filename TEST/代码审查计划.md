# 代码审查计划（Code Review Plan）

> 项目：EcgBpAnalysis（Holter 动态心电/动态血压分析系统）
> 技术栈：.NET Framework 4.6.2 / WinForms（双进程）+ native DLL（C/C++）
> 版本：v1.0　制定日期：2026-11-18　负责人：测试负责人
> 适用范围：所有新增/修改的 C#、C++、csproj、配置及数据库升级脚本

---

## 1. 目标与原则

| 项 | 内容 |
|---|---|
| 目标 | 在缺陷进入系统测试前拦截；建立可追溯的审查记录；针对医疗软件满足 IEC 62304 / ISO 14971 对开发与验证活动的证据要求 |
| 原则 | 风险驱动（越靠近患者数据/算法越严格）、就事论事、每个发现必须有结论（修复 / 豁免并说明理由）、审查全程留痕 |
| 准入 | 提交前作者已完成自审并附影响范围与自测结果 |
| 准出 | 所有发现项关闭或有签字豁免；P0 模块审查覆盖率 100% |

## 3. 项目特化审查清单（Checklist）

### A. P/Invoke 与 native 边界（最高优先级）

- `DllImport` 的 `CallingConvention=Cdecl`、`EntryPoint`、字符集是否与 C++ 导出一致；`StructLayout` / `MarshalAs` 字段顺序与长度是否逐字段对齐 native 结构体。
- 数组/指针参数的长度约定、谁分配谁释放、缓冲区是否可能溢出；返回码是否逐一检查。
- **DLL 产物一致性**：`libaecg.dll`、`libnibp_dynamic_d_d.dll`、`TransformZQ-x32/x64.dll` 的版本、位数（x86/x64）与调用方是否匹配；`LibNibp.vcxproj` 产出 `LibNibp.dll` 与 C# 调用的 `libnibp_dynamic_d_d.dll` 名称不一致的问题必须澄清。
- `lib\unmanaged\` 下 DLL 是否随安装包正确部署；缺失时是否有可诊断的失败提示。

### B. 数据完整性与解析逻辑

- CRC：`VerifyFileCRC` 开关、>500MB 跳过大文件、`crcs["crc"].Substring(2)` 的键/格式假设、`PadLeft` 比较 —— 是否所有分支都有正确的失败语义。
- 血压解析：`checksum` 校验、字节偏移与单位换算（`*1000`）、`TryParseExact` 失败时用 `DateTime.Now` 兜底（会污染数据时间）、`new DateTime(y,mth,d,h,m,s)` 未防非法日期抛异常、文件长度非 16/22 整数倍时的处理。
- 异常是否被 `catch` 吞掉、`Logger` 是否记录足够上下文。

### C. 全局状态与并发

- `GlobalVariables.AnaValues` 全局静态的读写是否跨线程；`async/await` 前后共享状态一致性；`ChangeTracker.AutoDetectChangesEnabled` 是否在所有路径恢复（如 `ParseBpFileFor8337` 的 try/finally）。

### D. 进程与外设通信

- 命名管道握手协议：超时、断连、消息粘包、子进程崩溃时的处理；`runas` 提权与单实例检查的正确性；退出时强杀子进程的副作用。

### E. 数据库与安全

- EF Core `DbContext` 生命周期与线程安全；`dbCheck.json` 升级脚本的幂等性与向后兼容；`ACCESS_KEY` 硬编码；AES 加密与患者隐私数据；加密狗许可校验。

### F. 通用项

- 空引用 / 越界 / 除零、资源释放（`FileStream` / `Bitmap` / SkiaSharp 对象 / `PrintDocument`）、硬编码路径与等待（`Task.Delay(1000)`）、注释掉的死代码、命名与重复封装（如两处 `nibp_figure_plot` 声明）。

## 4. 流程、角色与节奏

| 环节 | 内容 | 责任人 |
|---|---|---|
| 提交前自审 | 作者按清单自查，附影响范围与自测结果 | 开发者 |
| 同行审查 | PR / Change List，P0 模块强制双人 | Reviewer |
| 专项审查 | 安全、并发、native interop、数据库升级，按模块召集 | 测试负责人 + 模块 Owner |
| 问题闭环 | 发现项入台账，分级、指派、修复、复审、关闭 | 测试负责人跟踪 |
| 基线审查 | 对存量 P0 文件先做一轮基线审查，建立「已知问题清单」 | 测试负责人主导 |

## 5. 工具

- 静态扫描：Roslyn 分析器 + FxCop/CA 规则 + StyleCop。
- 评审与留痕：PR 平台 / Change List。
- 台账：见本目录《审查问题台账.md》（文件、行号、级别、结论、责任人、状态）。

## 6. 度量指标

- 审查覆盖率（P0 = 100%）
- 千行缺陷数
- 缺陷拦截率（审查发现 vs 系统测试发现）
- 平均修复周期
- 复审通过率
- 已知问题清单收敛趋势

## 7. 审查问题分级

| 级别 | 定义 | 处理要求 |
|---|---|---|
| **阻断（Blocker）** | 崩溃、数据损坏、算法结果错误、患者数据泄露 | 必须修复，禁止合入 |
| **严重（Major）** | 主要功能受损、边界条件错误、并发隐患 | 必须修复或签字豁免 |
| **一般（Minor）** | 局部逻辑瑕疵、可维护性、性能隐患 | 计划内修复 |
| **建议（Info）** | 命名、注释、风格 | 可选 |
