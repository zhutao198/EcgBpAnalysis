# 测试计划（Test Plan）

> 项目：EcgBpAnalysis（Holter 动态心电/动态血压分析系统）
> 技术栈：.NET Framework 4.6.2 / WinForms（双进程）+ native DLL（C/C++）
> 版本：v1.0　制定日期：2026-11-18　负责人：测试负责人
> 配套文档：《代码审查计划.md》《审查问题台账.md》《测试缺陷台账.md》《测试用例库.md》

---

## 1. 测试策略

采用 **V 模型 + 医疗器械软件生命周期**思路：需求 → 设计 → 编码 对应 验收 → 系统 → 集成 → 单元测试。

由于核心算法在 native DLL 且无 C# 源码，采用「**黑盒 golden data 回归为主、C# 层白盒单元/集成测试为辅**」的组合策略。

**当前测试现状**：全仓库仅 3 个散落脚本（`TestSyntax.cs`、`TestSkiaSharp.cs`、`TestSKSurfaceDraw.cs`），无正式测试项目、无测试框架、无 CI。因此第一优先级动作是建立测试工程并接入 CI。

## 2. 测试层级与分工

| 层级 | 对象 | 手段 | 目标 |
|---|---|---|---|
| 单元测试 | 可独立运行的 C# 纯逻辑 | 新建测试项目（**NUnit/MSTest + Moq**），对 `FileDataHandler`、`DbChecker`、时间/CRC/统计计算等做隔离测试 | 覆盖解析、校验、计算的边界与异常 |
| 集成测试 | P/Invoke、数据库、进程通信、文件导入全链路 | 测试程序调用真实 DLL / SQLite / 命名管道 | 验证跨边界契约与数据流 |
| 系统测试 | 完整双进程产品 | 手工 + UI 自动化（WinAppDriver） | 端到端业务流程、功能、性能、兼容 |
| 验收测试 | 需求 / 临床场景 | 基于需求与用户场景的验收用例 | 交付准入 |

## 3. 重点测试用例设计（示例，贴合真实代码）

### 血压文件解析（`FileDataHandler.ParseBpFile` / `ParseBpFileFor8337`）
- 正常样本：16/22 字节结构、checksum 正确 → 字段值、`*1000` 单位、`caseId` 均正确入库。
- checksum 错误 → 不入库；文件长度不足 / 非整数倍 → 不崩溃、有日志。
- 时间字段非法（如月=13、日=32）→ 当前 `new DateTime` 会抛异常，验证是否已防护；`TryParseExact` 失败时是否错误写入 `Now`。
- 边界值：收缩压/舒张压=0（数据状态）、极值、负数、袖带/测量类型枚举越界。

### CRC 校验（`Crc32Verify` / `Crc32Verify_IE95`）
- 篡改任一 `holter-*` / `nibp-*` 文件 → 返回失败；缺失 crc 文件 → 返回失败；`VerifyFileCRC=false` → 跳过。
- >500MB 文件被跳过的行为是否符合设计；crc 文件格式异常（`Substring(2)`、键缺失）是否健壮。

### ECG 算法（golden data 回归）
- 用 **MIT-BIH Arrhythmia Database** 等标准库作为输入，固化基线结果（QRS 计数、心搏分型、HRV 时/频域、ST、QTc、AF 事件），每次 DLL / 代码变更做回归比对，容差内通过。
- 覆盖导联脱落、起搏信号、房颤/房扑、成对早搏等场景（`CommonMethods.cs:516` 的 TODO 段重点验证）。

### 报告与打印
- 多页分页、长患者信息、异常值、预览/打印一致性。

### 进程与外设
- 握手超时、子进程被强杀 / 崩溃、重复启动、SD 卡拔出 / 损坏文件、蓝牙断连、8337 直连上传。

### 数据库
- `dbCheck.json` 从旧版本升级的幂等性；并发写入；加密字段读写往返。

## 4. 测试数据与环境

- **数据**：标准公开库（MIT-BIH 等）+ 合成边界数据 + **脱敏**真实数据（遵守患者隐私）；golden 结果需版本化并标注来源与生成时的 DLL 版本。
- **环境矩阵**：Windows 版本 × x86/x64 × .NET Framework 4.6.2 × 管理员权限；外设：SD 卡（模拟/真实）、蓝牙 ABPM、8337 直连、加密狗；native DLL 的 Debug/Release 与位数组合。

## 5. 缺陷管理与准入/退出标准

- **分级**：P0 崩溃/数据错误/算法结果错误（阻塞发布）、P1 主要功能受损、P2 一般、P3 体验/外观。
- **流程**：提报 → 分级 → 指派 → 修复 → 复审 → 关闭；每轮生成缺陷趋势与遗留风险评估。
- **退出标准**：
  - P0 / P1 全部关闭；
  - P0 模块审查与单元测试覆盖率达标（建议行覆盖 ≥70%，核心解析/校验 ≥90%）；
  - golden data 回归全部通过；
  - 系统测试主要业务流程通过率 100%；
  - 遗留风险经评审签字。

## 6. 可追溯性矩阵（RTX）

建立 **需求 / 风险 → 设计 → 代码文件 → 测试用例 → 结果** 的 RTX 矩阵，确保每条核心需求和每个已识别风险都有对应测试证据 —— 医疗软件审计的关键产物。模板见《测试用例库.md》附录。

## 7. 主要风险与应对

| 风险 | 应对 |
|---|---|
| native DLL 无源码，无法白盒 | golden data 黑盒回归 + 接口契约测试 + 版本变更强制全量回归 |
| 依赖真实硬件 | 硬件模拟器 + 录制回放数据 + 分阶段真机验证 |
| 存量代码无测试、耦合高 | 先建「特征化测试（characterization test）」锁定现有行为，再逐步重构 |
| x86/x64 DLL 混用 | 环境矩阵中显式验证位数匹配 |
