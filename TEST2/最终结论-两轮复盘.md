## 三、不一致项清单与裁决（8 项）

### U-01 ⚠️ 阻断项遗漏：R001（NIBP 输出缓冲区越界）
- **第一轮**：R001 —— **阻断级**，唯一阻断项，状态"待确认（需 native 接口定义）"。
- **第二轮**：**台账中无对应条目**；仅在《native契约差异清单》"无法核对项"提到 NIBP 契约缺失，未登记为审查发现/缺陷。
- **代码复核（本轮完成）**：**成立**。
  `BpPulseWaveDataHandler.cs:31-36` 按 `arrData.Length` 分配 `dc/ac/fitCurveX/fitCurveY`、按固定 100 分配 `stepDc/stepDcLen`；
  `:61-68` 回读时 `Marshal.Copy(outputWave.dc, dc, 0, dc.Length)`，其中 `dc.Length == outputWave.len`（由 native 决定）。
  若 native 返回 `len > arrData.Length` 或 `stepLen > 100`，即从非托管缓冲区**越界读取**。
  同文件 `:42` 仅设置 `input.refPR`，**未设置 `refHR` 与 `cl`** → R002 亦成立。
- **裁决**：**保留 R001 为最终台账唯一阻断项**，并补入 R002。第二轮未推翻，仅未收录。
- **处置**：修复仍需 native 侧提供 `F:\temp\figurePlot` 头文件（外部资源阻塞不变）。

### U-02 ⚠️ 定级分歧：报告 NaN/∞ 类问题
- **第一轮 R034**（报告占比除零 → NaN/∞）= **严重**；**第二轮 T2-R-053**（LF/HF 除零 → "∞"）= **一般**。
- **复核**：两者**同类同影响面**——均为"除零结果直接写入报告"。T2-R-053 另有"空串 → `FormatException` 中断 `CalcData` → 报告其它数值全为 0"分支，影响不亚于 R034。
- **裁决**：**统一升级 T2-R-053 为"严重"**；R034 维持严重。两条对象不同（占比 vs LF/HF），均保留。

### U-03 ⚠️ 定级分歧：native 契约类问题
- **第一轮**：R001=阻断、R002/R035=严重、R040（out IntPtr 无释放契约）=一般。
- **第二轮**：T2-R-043/044（testWave 原型不一致）=**严重**；T2-R-045（libnibp 未入版本库）=严重。
- **裁决**：native 契约类问题**整体按"涉及未托管内存 / 静默数据错位"提级**——
  T2-R-043/044 维持严重；**R040 由"一般"提为"严重"**（9 处 out IntPtr 无释放 API，属未托管内存泄漏）。
  理由：此类问题一旦发生即为进程级故障，医疗软件不可接受。

### U-04 ℹ️ 应合并：libnibp 交付问题
- **第一轮 R012**：LibNibp 产物名 `LibNibp.dll` 与 C# 调用名 `libnibp_dynamic_d_d.dll` 不一致；C++ 源码在 `F:\temp\figurePlot`（仓库外）→ 不可构建。
- **第二轮 T2-R-045**：该 DLL 未纳入版本控制（仅存在于 gitignore 的 bin 历史产物）。
- **裁决**：**同属 libnibp 交付/可重现性**，最终台账合并为一条，保留两个证据点，统一编号。

### U-05 ℹ️ 非重复：两处血压时间解析
- **第一轮 R004**：`FileDataHandler.cs:98-100` **文件名**时间解析失败 → `out` 参数被置为 `DateTime.MinValue`(0001-01-01)（与"用 Now 兜底"的注释意图相反）；`:156` 8337 非法日期致整批丢失。
- **第二轮 T2-R-009**：`CommonFuns.cs:348-385` **holter.ini** 采集开始时间解析失败 → 静默变成 `1970-01-01`。
- **裁决**：**位置不同、失效值不同，是两处独立缺陷，互补保留**。R004 已被第二轮 T2-R-005（8337 整批丢失）以行为证据独立确认。
  R004 的 `MinValue` 结论经复核**正确**（`TryParseExact` 失败时 `out` 置 default，而非保留初值 `Now`）。

### U-06 ⚠️ 测试用例构造缺陷：TC-PIPE-08 未真正触发 R005
- **第一轮 R005**：`ParseBpFileFor8337` 仅校验 `Length < 22`，尾部不足 22 字节时 `BitConverter.ToInt16(dataBytes, i+6)` 越界读。
- **第二轮 TC-PIPE-08**：构造 `22 + 17 = 39` 字节 —— 末轮 `i=22` 尚余 17 字节，读 `offset=28/29` **仍在缓冲区内**，**未触发越界**，仅观察到"返回 null"。
- **裁决**：R005 **成立**（越界读发生于 `length % 22 ∈ [1,7]`，如 29 字节时读 `28/29` 越界）；TC-PIPE-08 的输入构造**未命中该路径**，用例名与实际覆盖不符。
- **处置**：已修正 TC-PIPE-08 的输入构造（改用 `length % 22 == 7` 的样本）并补充断言说明，见 §六。

### U-07 ℹ️ 缺口：R003（CRC >500MB 跳过仍返回成功）
- **第二轮无对应条目**；但第二轮 T2-R-008（CRC 单次 `ReadAsync` 未读满 → 完好数据误判损坏）**已实证同一函数 `Crc32Verify` 的另一缺陷**。
- **代码复核**：R003 **成立** —— `FileDataHandler.cs:25` 与 `:60` 的 `if (fi.Length < 524288000)` 使超 500MB 文件**完全不校验**，函数仍 `return true`。
- **裁决**：**保留 R003**；与 T2-R-008 互补（前者=跳过大文件，后者=读不满小文件）。

### U-08 ℹ️ 缺口：R043（缺加密狗静默退出，退出码 0）
- **第二轮无对应条目**，但第二轮的 UI 冒烟实证（`TEST/SystemTests/AppLaunchSmokeTests.cs`）**重现了同一行为**。
- **裁决**：**保留 R043**（第一轮已由 UI 冒烟独立取证）。
